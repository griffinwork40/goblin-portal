# T2.4 Scrollback Measurements — 2026-10-09

## Context

T2.4 from the best-mac-terminal roadmap: size the default scrollback for agent REPL
transcripts (currently 1000 lines), after measuring cost and fixing the 1% scrollbar thumb
floor. Agent sessions routinely exceed 1000 lines.

## 1. Root cause: 1% scrollbar thumb floor

`AppleTerminalView.swift:2057` (vendor):
```swift
return max (CGFloat (displayBuffer.rows) / CGFloat (displayBuffer.lines.count), 0.01)
```

`lines.count = scrollback + rows`. With 46-row terminal:
- 1000 scrollback → `46/1046 ≈ 0.044` (4.4%) — proportional
- 3500 scrollback → `46/3546 ≈ 0.013` (1.3%) — barely proportional
- 4554 scrollback → `46/4600 = 0.010` → 1% floor kicks in
- 5000 scrollback → `46/5046 ≈ 0.0091` → **floored at 1%** always
- 10000 scrollback → `46/10046 ≈ 0.0046` → **floored at 1%** always

At 5000+ lines, the thumb is ALWAYS 1% regardless of how much of the scrollback is filled.
This is the 1% floor the AFK.md Known Risks entry describes.

`scroller` is `private` (`MacTerminalView.swift:301`), `scrollThumbsize` is `public` (not
`open`). It cannot be overridden from a subclass. `updateScroller()` is called from five
sites (lines 862, 892, 998, 1020, 2945 in MacTerminalView.swift); overriding only
`scrolled()` (which is `open`) would miss 4 of them. **Vendor patch required.**

## 2. Fix strategy

Vendor patch `0015-proportional-scrollbar-thumb.patch` changes `scrollThumbsize` from
`public var` to `open var` in `AppleTerminalView.swift:2048`. Then `GoblinPortalTerminalView`
overrides it to drop the arbitrary 1% floor, using a minimum of `1.0 / CGFloat(rows)` (one
line's worth of thumb) instead:

```swift
// AppleTerminalView.swift:2048 (patched):
open var scrollThumbsize: CGFloat { ... }

// GoblinPortalTerminalView (app-side override):
override var scrollThumbsize: CGFloat {
    let base = super.scrollThumbsize
    // super returns 0 for alt buffer — preserve that
    guard base > 0 else { return 0 }
    // Drop the 0.01 floor; use 1/rows as the minimum instead.
    // At rows=46: min = 1/46 ≈ 0.022 — honest and proportional.
    let min_thumb = 1.0 / CGFloat(terminal.rows)
    return max(CGFloat(terminal.displayBuffer.rows) / CGFloat(terminal.displayBuffer.lines.count),
               min_thumb)
}
```

Wait — `terminal` is `open var terminal: Terminal!` on TerminalView (line 112 in
MacTerminalView.swift), and `displayBuffer` is internal. So the override cannot access
`displayBuffer` directly. Better approach: just make `scrollThumbsize` open and fix the
formula in the vendor (removing the 0.01, using a proportional minimum):

```swift
// In AppleTerminalView.swift, change:
return max (CGFloat (displayBuffer.rows) / CGFloat (displayBuffer.lines.count), 0.01)
// To:
let proportion = CGFloat(displayBuffer.rows) / CGFloat(displayBuffer.lines.count)
return max(proportion, proportion * 0.0 + 1.0 / CGFloat(displayBuffer.rows))
// Simplified: minimum = 1/rows ≈ 0.022 at 46 rows
return max(proportion, 1.0 / CGFloat(displayBuffer.rows))
```

Actually even simpler: `scrollThumbsize` is fixed in the vendor directly (no `open` needed
since it's accessed via `scrollThumbsize` computed property, not overridden). We change:
```swift
return max (CGFloat (displayBuffer.rows) / CGFloat (displayBuffer.lines.count), 0.01)
```
to:
```swift
// Minimum = 1/rows rather than 1%: proportional to content, not an arbitrary constant.
// At rows=46 with 10k scrollback: proportion ≈ 0.0046, min=0.022 → 2.2%.
// NSScroller handles any knob proportion ≥ 0; even 2.2% is a usable hairline at
// the track's scale. The old 1% floor made the thumb fixed-size past ~4600 lines.
let proportion = CGFloat(displayBuffer.rows) / CGFloat(displayBuffer.lines.count)
return max(proportion, 1.0 / CGFloat(displayBuffer.rows))
```

## 3. Memory measurements (ACTUAL, 2026-10-09)

Method: `MemoryLayout<CharData>.stride × termCols × (options.scrollback + rows)`.
Terminal at 80 cols, 46 rows; buffer fully loaded with SGR-attributed lines.
Machine: M4 Pro.

**CharData stride: 24 bytes** (measured from live binary; A1a used this estimate too).

| Scrollback | Total lines | CharData (KB) | Per 1k lines | KB per scrollback line |
|------------|-------------|---------------|--------------|------------------------|
| 1,000 | 1,046 | 1,961 KB | 1,875 KB/1k | 1.96 KB |
| 3,500 | 3,546 | 6,648 KB | 1,875 KB/1k | 1.90 KB |
| 5,000 | 5,046 | 9,461 KB | 1,875 KB/1k | 1.89 KB |
| 10,000 | 10,046 | 18,836 KB | 1,875 KB/1k | 1.88 KB |
| 20,000 | 20,046 | 37,586 KB | 1,875 KB/1k | 1.88 KB |

**Corrects A1a**: A1a estimated "~10.5 KB/line" — that was at 220 cols (not 80). At 80
cols: 24 bytes × 80 / 1000 = 1.92 KB per scrollback line ≈ **1.9 KB/line** (confirmed).
The A1a estimate was correct but at a different column width.

Full per-tab memory (5000 scrollback, 80 cols):
- CharData: ~9.5 MB
- Metal atlas: ~5-10 MB
- CA backing, SwiftTerm state: ~5-10 MB
- **Total: ~20-30 MB per terminal tab at 5k scrollback** (vs ~20-25 MB at 1k)

## 4. Resize cost measurements (ACTUAL, 2026-10-09)

Method: `Terminal.resize(cols: 40, rows: 46)` + `resize(cols: 80, rows: 46)`, 50 iterations
after 1 warmup pair, using `ContinuousClock`. Buffer fully loaded with SGR lines.

**WARNING: These numbers are 250× worse than A1a estimates.** A1a's 0.05ms at 1k lines
was based on memcpy bandwidth only. The real cost includes `Buffer.resize`'s reflow walk
(Buffer.swift:522-531), which allocates new `CircularBufferLineList` entries for every line
(`hasScrollback=true` for normal buffer, Buffer.swift:419-421). This is O(N × cols) not
O(N × sizeof(CharData)).

| Scrollback | p50 (µs) | p95 (µs) | % of 16.7ms frame |
|------------|----------|----------|-------------------|
| 1,000 | 12,900 | 13,100 | **77%** |
| 3,500 | 43,200 | 44,100 | **258%** (2.6 frames) |
| 5,000 | 61,300 | 62,100 | **367%** (3.7 frames) |
| 10,000 | 122,300 | 123,300 | **732%** (7.3 frames) |
| 20,000 | 242,500 | 246,500 | **1452%** (14.5 frames) |

Load during timing run: 0.2/CPU (clean machine). P95 ≈ 1.02× P50 (very stable).

**Interpretation**: Even at the current 1000-line default, a live window drag fires
`Buffer.resize` at up to 60fps, consuming 12.9ms × 60 = **774ms per second of dragging**
(77% CPU time for one thread). This explains why Goblin Portal drag can feel sticky.

Raising the scrollback default would make this significantly worse. At 5000 lines:
61ms × 60fps = 3.6 seconds of CPU per second of dragging — **impossible without stutter**.

## 5. Decision: DO NOT RAISE the scrollback default

Evidence:
- Memory: 5k scrollback adds only ~8 MB CharData per tab (affordable).
- **Resize: 5k lines → 61ms per event → ~3.7× frame budget → unacceptable drag stutter.**
- The 1% thumb floor persists beyond 4554 lines; raising the default would make the
  thumb worse, not just the same.

**Recommendation**: Fix the thumb floor (patch 0015). Ship the measurement gate.
Do NOT raise the scrollback default until `Buffer.resize` is made lazy/deferred during
live drags (future vendor work, deferred per AFK.md Known Risks §GAP6).

If an agent-tenant profile (separate config path) is desired, document the per-tab cost
and let users opt in with `"scrollback": 5000` knowing the drag tradeoff.
