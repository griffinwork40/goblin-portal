# T3.1 keystroke latency (2026-10-18 .. 2026-10-19)

Status: **DROPPED (2026-10-19, third run, verdict below supersedes the two earlier "DROP"
sections).** The vendored `LocalProcess.swift` is upstream `dd2fb8ac` again (sha256 `97a77317...`),
`verify-vendor.sh` reports 15 patches, and no gate ships. Artifacts for re-running this
experiment are in `t3.1-keystroke-latency/` next to this file.

## Final verdict (supersedes everything below)

**The direct-write delta is real but fragile and imperceptible, so patch 0016 does not ship.**

Why the two earlier "DROP confirmed" runs were right for the wrong reason: every design that
showed "no delta" was INTERLEAVED. "Probe (a)" was meant to be separate single-arm processes,
but each of its 10 runs was the interleaved `latency` mode, so it repeated the interleaved
measurement ten times. The only non-interleaved probe (block, direct first) showed +56/+86 us,
and its "warm/cold" explanation predicts the wrong sign (the cold first block won).

Third run (patch rebuilt from the described design, M4 Pro, quiet machine, release SwiftTerm.o):
correctness `fdflags`/`order`/`full` all pass (worst `send()` 282 us with a stopped reader).

| Design | direct p50 | DispatchIO p50 | delta |
|---|---|---|---|
| Single-arm separate processes, 10 ABAB pairs | 109.9 us | 172.5 us | **+62.5 us, direct wins 10/10** |
| Blocks AB (direct first), 3 runs | ~110 us | ~174 us | **+63 us** (median) |
| Blocks BA (DispatchIO first), 3 runs | ~174 us | ~173 us | **-1.0 us** (median) |

Raw: `t3.1-keystroke-latency/separate_process_runs.log`, `block_runs.log`.

What this shows: the contamination hypothesis is TRUE and one-directional. Once a DispatchIO
write has run in a process, later direct writes are as slow as DispatchIO for at least the
following 100-sample block (~0.2 s+). That is why every interleaved design read ~0.

Decision rule, fixed before the run: KEEP only if blocks show >= 20 us in BOTH orders AND the
separate-process pairs show >= 20 us with >= 8/10 wins. BA fails, so **DROP**. On the merits:
- In the patched app every paste > 1024 bytes goes through DispatchIO. Pasting prompts into an
  agent REPL is this app's core workflow, so the benefit would likely vanish early in a pane's life.
- At best it is 62 us at p50, about 0.4% of a 16.7 ms frame. The whole key-to-echo pty round
  trip is ~0.1-0.2 ms; key-to-photon is dominated by vsync and the display, not this hop.

Not measured (the only path to a perceptible win): p99 under heavy CPU load, where GCD
scheduling of the DispatchIO worker could add milliseconds, and how long the contamination
lasts after one async write. Reopen T3.1 only with a fixed rule such as "direct improves
loaded p99 by >= 0.5 ms AND contamination clears within 1 s". Draft patch:
`t3.1-keystroke-latency/0016-sync-small-writes.draft.patch` (apply with `patch -p1` inside
`vendor/SwiftTerm`); harnesses alongside it.

The `check-input-latency.sh` gate added during this work was removed: with the patch dropped it
could only ever exit 1, and a permanently red gate protects nothing.

## Measurements (M4 Pro, release SwiftTerm.o, load 5.6-18.7 on 14 CPUs)
- pty master IS O_NONBLOCK (libdispatch sets it).
- Correctness passes both ways: `order` (64 KiB paste + 200 keys arrive in order) and `full`
  (raw-filled pty until EAGAIN, so the direct path's EAGAIN fallback runs; worst send() 180 us,
  every byte arrives after SIGCONT).
- SEPARATE processes per mode (3 rounds, alternated): DispatchIO p50 109-165 us, direct p50 23-84 us,
  so a delta of about 80-110 us.
- INTERLEAVED in one process (random order within each pair, 600 pairs, 2 ms cadence): **no delta**
  (p50 delta +0.3 us and -0.2 us). The async/async control is also flat (0.5, 0.6 us).
- The whole key-to-echo round trip is about 0.05-0.15 ms. The roadmap's "45-65 ms structural" estimate
  is not this hop. Even the best-case delta (about 0.1 ms) is under 1% of a 16.7 ms frame.

## Open question that decides keep/drop
Is the separate-run delta drift between processes, or does one arm contaminate the other in the
interleaved run? One possibility: an outstanding DispatchIO write op on the shared fd entry slows
the read channel, and that cost lands on the next sample whichever arm it is.
Next probe:
(a) 10+ alternating separate processes per mode (ABAB...) at matched load;
(b) interleaved with a long gap (50 ms) between samples;
(c) interleaved blocks (100 direct, then 100 DispatchIO).
If (a) shows the delta and (b)/(c) show contamination, the interleaved gate design is wrong. Otherwise
DROP the patch per the roadmap rule ("must show a delta or the patch is dropped").

## Probe results (2026-10-19, check-input-latency.sh, M4 Pro, release SwiftTerm.o)

Machine: 14 CPUs, load1=4.27 at run start (well under 0.70/cpu threshold).
All three probes ran via `check-input-latency.sh` (W1b, 308 LOC).

### Control noise floor
Both arms DispatchIO (600 pairs, 2ms cadence):
- dispatchio-A: p50 167.1 µs  p95 218.5 µs  p99 319.2 µs  max 694.0 µs
- dispatchio-B: p50 166.4 µs  p95 220.8 µs  p99 341.9 µs  max 794.6 µs
- RESULT: p50_delta=0.8 µs, p95_delta=-2.2 µs — noise floor well within 20 µs bar.

### Probe (c) — block mode (100 direct then 100 DispatchIO, no interleaving)
- direct:     p50  93.6 µs  p95 164.3 µs  p99 221.4 µs  max 221.4 µs
- dispatchio: p50 179.2 µs  p95 215.1 µs  p99 358.2 µs  max 358.2 µs
- RESULT: p50_delta=85.6 µs — **PASS** (≥20 µs)

### Probe (b) — gap mode (300 pairs, 50ms inter-sample gap)
- dispatchio: p50 202.8 µs  p95 331.8 µs  p99 397.8 µs  max 767.2 µs
- direct:     p50 203.2 µs  p95 332.2 µs  p99 363.0 µs  max 394.3 µs
- RESULT: p50_delta=-0.4 µs — **no delta**

### Probe (a) — ABAB alternating processes (10 runs, SWIFTTERM_SYNC_WRITE alternated)
Individual run p50_delta values (latency mode, 100 pairs each):
- run 1 (direct):     +0.7 µs
- run 2 (dispatchio): +0.2 µs
- run 3 (direct):     -1.2 µs
- run 4 (dispatchio): +1.0 µs
- run 5 (direct):     +0.8 µs
- run 6 (dispatchio): +0.8 µs
- run 7 (direct):     +0.4 µs
- run 8 (dispatchio): +1.7 µs
- run 9 (direct):     -1.0 µs
- run 10 (dispatchio):+0.1 µs
- Mean delta (direct - DispatchIO) = **-0.8 µs** — **no delta**

### Synthesis
1/3 probes showed delta ≥ 20 µs (probe (c) only). 2-of-3 rule not met.

**Interpretation:** Block mode (probe c) runs the two arms in separate 100-sample
sequential blocks within the same process. It shows an 85.6 µs delta. But gap mode
(probe b, 300 pairs, 50ms gap) and ABAB (probe a, 10 separate process invocations)
both show ~0 µs. The gap between block and interleaved results is the key signal:

- The block design measures **two different steady states** of the same process — the
  direct-write block runs first with no DispatchIO history; the DispatchIO block runs
  second after the direct block has already warmed all the caches. The 85.6 µs block
  delta likely reflects this warm/cold asymmetry, not a real keystroke benefit.
- Gap mode (50ms settling) and ABAB (fresh processes) both agree: **no delta**.
- The original interleaved finding (+0.3/-0.2 µs) was not fd-entry contamination
  hiding a real delta — it was the correct measurement. The patch genuinely does not
  help in the interleaved (real-world) design.

**Root cause understanding:** The pty round-trip latency (~100-200 µs) is dominated by
process scheduling cost (waking `cat`, not the write syscall). The DispatchIO dispatch
overhead (~80-110 µs measured in separate processes) is real but is absorbed entirely
by run-loop scheduling variance when measured in the same process with the same fd.
Bypassing DispatchIO saves a closure enqueue but the key is still waiting for the child
process to be scheduled — that wait swamps any write-path saving.

## DECISION: DROP

Patch 0016 does not earn its keep. The roadmap rule is "show a delta or drop the patch."
The interleaved measurement (the correct design for a single running process) shows no
delta across all interleaved probes (gap mode, ABAB, original latency mode).
